# PodcastHub 小程序项目说明与总体计划

> 版本：v0.2
> 状态：规划中（核心浏览 + 创作者模块已完成）
> 适用对象：产品 / 设计 / 开发 / Claude Code / 后续接手的协作者

## 1. 项目目标

PodcastHub 小程序的目标，是把现有 Web 站中的核心能力，以更轻、更顺手的方式放到微信生态里，让用户可以在移动端更快完成以下动作：

1. 找到合适的录音室
2. 发现创作者（剪辑师/制作人）
3. 查看录音室详情、价格、地址、联系方式、交通信息
4. 通过飞书表单提交自己的录音室
5. 提交反馈、补充评价、修正信息
6. 让管理员在轻量流程下完成审核与上线

### 核心原则

- **录音室优先**：主任务始终是录音室发现与选择
- **创作者发现**：让用户快速发现剪辑师和制作人，形成"找场地 + 找人"双入口
- **轻量优先**：小程序只做"最常用的动作"
- **信息清晰**：每个页面只承担一个主要任务
- **可持续扩展**：后续可以接入更多商务资源，但不抢主线
- **可维护**：后续 Claude Code 可以按文档逐步施工，而不是一次性重构

## 2. 产品边界

### 2.1 小程序第一期要做什么

第一期建议覆盖：

- 录音室列表（TabBar 主入口）
- 创作者列表（TabBar 第二入口：剪辑师 + 制作人）
- 录音室详情
- 创作者详情
- 提交录音室
- 通用反馈
- 管理员登录
- 管理员基础管理

### 2.2 第一期开始不做什么

以下内容建议暂缓：

- 复杂评论社区
- 复杂多人协作后台
- 复杂权限系统
- 复杂实时同步
- 过重的商务资源完整模块
- 小程序内直接编辑所有线上数据的复杂表单系统

### 2.3 小程序与现有 Web 的关系

建议采用下列分工：

- **Web 端**：完整展示、编辑、后台管理、审批同步、地图
- **小程序端**：轻量浏览、轻量提交、轻量反馈、轻量登录后查看部分后台能力

小程序不是 Web 的重复副本，而是新的移动入口。

## 3. 目标用户

### 3.1 普通访客

需求：

- 通过手机快速看录音室
- 看地址、价格、预约方式、交通信息
- 发现剪辑师和制作人
- 判断是否适合自己

### 3.2 录音室主理人

需求：

- 快速提交自己的录音室
- 了解被收录后的展示效果
- 对信息进行补充或纠错

### 3.3 管理员

需求：

- 审核提交内容
- 修正信息
- 删除失效录音室
- 同步飞书结果表与线上数据

## 4. 第一版页面地图

### 4.1 录音室（TabBar 主入口）

录音室页应该回答一个问题：

> "我现在最适合去哪间录音室？"

录音室页定位：**搜索 + 城市筛选 + 卡片列表 + 操作入口**

录音室页包含：

- 搜索栏（按名称/地址实时搜索，带清除按钮）
- 城市筛选 chips（全部 + 9 个城市，点击切换，支持反选）
- 结果摘要（当前城市 + 总数）
- 录音室卡片列表（封面图 + 名称 + 收费方式 + 容纳人数 + 地址）
- 底部操作按钮："提交录音室"（主按钮）+ "意见反馈"（次按钮）

> 录音室页是 TabBar 首页主入口，承担录音室发现与浏览的核心功能。
> 筛选、比较、搜索在本页完成；决策、预约、交通确认交给详情页。

### 4.2 创作者（TabBar 第二入口）

创作者页应该回答：

> "有哪些剪辑师和制作人可以合作？"

创作者页定位：**分段切换 + 搜索 + 创作者卡片列表**

创作者页包含：

- 分段控件（Segment Control）：剪辑师 / 制作人，切换加载对应列表
- 搜索栏：实时搜索创作者
- 创作者卡片列表：头像 + 名称 + 标签 + 简介
- 空状态："正在入驻中"友好提示

### 4.3 创作者详情

详情页应该回答：

> "这位剪辑师/制作人值不值得合作？"

建议包含（按类型条件渲染）：

- 共享头部：头像 + 名称 + 标签 + 简介
- 剪辑师特有：擅长技能、作品展示、报价、合作评价
- 制作人特有：行业领域、服务类型、联系方式

### 4.4 录音室详情

详情页应该回答：

> "这间录音室值不值得去？"

建议包含：

- 名称
- 描述
- 地址
- 预约方式
- 开放时间
- 价格
- 联系方式
- 交通枢纽预估
- 图片

### 4.5 提交录音室

提交页应该回答：

> "我怎么把我的录音室提交给 PodcastHub？"

建议做成：

- 轻量引导页
- 跳转飞书表单
- 如有需要可加站内说明与字段说明

### 4.6 反馈页

反馈页应该回答：

> "我怎么告诉你这里需要改进？"

建议承接：

- 通用反馈
- 功能期待
- 信息更正
- 使用体验建议

### 4.7 管理员登录 / 管理页

建议包含：

- 游客态 / 管理员态区分
- 密码验证
- 录音室编辑
- 删除
- 审核
- 同步工作流

## 5. 信息架构原则

### 5.1 录音室主入口 vs 创作者入口

录音室 Tab 是**发现录音室的主入口**，偏"找场地"和"比较选择"。
创作者 Tab 是**发现人的入口**，偏"找剪辑师/制作人"。
两个 Tab 各自独立，互不干扰，形成"找场地 + 找人"双入口。

### 5.2 详情页要像"决策页"

详情页不是展示越多越好，而是要让用户快速决策：

- 这是什么地方/人
- 在哪/擅长什么
- 贵不贵/报价多少
- 怎么预约/联系
- 怎么去（录音室）

### 5.3 反馈入口要低打扰

反馈与更正入口不能抢主流程，但要容易找到（录音室页底部操作区）。

### 5.4 管理能力不能裸露

管理员能力必须和游客态分开，不可默认暴露。

## 6. 推荐技术路线

### 6.1 前端

建议使用：

- Taro + React + TypeScript

原因：

- 和现有 Web 技术栈接近
- Claude Code 容易理解
- 迁移和复用成本低
- 微信小程序生态适配成熟

### 6.2 后端

继续复用现有：

- FastAPI
- SQLAlchemy
- Supabase Postgres
- Supabase Storage

### 6.3 资料工作流

继续复用现有飞书链路：

- 飞书问卷：收集
- 飞书结果表：整理与删改
- 线上数据库：最终发布源
- 同步前先 diff，再人工确认
